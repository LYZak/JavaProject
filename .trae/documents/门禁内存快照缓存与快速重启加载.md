## 目标与范围
- 将“门禁判定所需的内存快照”（当前由 AccessRequestProcessor 启动时从 SQLite 全量装载）在程序退出时打包落盘。
- 程序重启时优先从该缓存文件恢复；当缓存不存在/损坏/过期时回退到数据库读取。

## 现状定位（已确认）
- 启动时从 DB 全量装载到内存的位置是 AccessRequestProcessor 的 `AccessControlContext`（users/badges/resources/resourceGroups/userProfiles 等）。
- 目前没有统一的退出钩子（未使用 shutdown hook / windowClosing 监听），DatabaseManager.close() 也未在正常退出路径调用。

## 设计方案
- **缓存对象**：以 AccessRequestProcessor 的 `AccessControlContext` 作为缓存内容（这是系统“不能访问数据库、必须在内存判定”的关键数据）。
- **缓存文件位置**：默认 `data/cache/access_context.bin`（目录不存在则创建）。
- **一致性/失效判断**：缓存文件内写入元信息（版本号、保存时间、保存时的 DB 文件 lastModified）。启动时比对当前 `data/access_control.db` 的 lastModified；不一致则认为缓存过期，回退 DB。
- **写入安全**：先写到临时文件（同目录），再原子替换为正式文件，避免异常退出造成半截文件。

## 代码改动点（不新增依赖）
1) **模型类可序列化**
- 给 `User` / `Badge` / `Resource`（以及实际被快照引用到的其它模型，如需要）增加 `implements Serializable`，以便用 JDK 原生 ObjectOutputStream 落盘。

2) **AccessRequestProcessor：读写缓存 + 启动优先缓存**
- 在构造函数中：`尝试从缓存加载 -> 成功则使用缓存 context -> 否则走现有 loadDataIntoMemory()`。
- 增加 `persistContextToCache()`：把当前 `context` 封装到一个可序列化的 Envelope（含元信息）并写入缓存文件。
- 允许通过系统属性覆盖缓存路径（例如 `-Daccesscontrol.cacheFile=...`），便于测试。

3) **AccessControlSystem：统一 shutdown**
- 新增 `shutdown()`：调用 `accessRequestProcessor.persistContextToCache()`，然后 `dbManager.close()`。

4) **MainWindow：注册退出钩子**
- 在 MainWindow 构造完成后注册 `Runtime.getRuntime().addShutdownHook(...)`，确保：点击窗口关闭 / 菜单 Exit / System.exit 都会触发缓存落盘。

## 测试与验证
- 新增/扩展 JUnit：
  - 使用 `jdbc:sqlite::memory:` 构造最小数据（插入 user/badge/resource/profile/group 关系），先让 ARP 从 DB 装载；然后调用 `persistContextToCache()`；再创建新的 ARP 并强制走缓存加载；断言关键 Map 的 size/关键键存在一致。
  - 覆盖“缓存损坏/元信息不匹配”时回退 DB 的路径。

## 风险与应对
- 缓存序列化版本演进：Envelope 增加 `cacheVersion`，未来字段变化时可通过版本号回退 DB。
- 异常退出导致缓存不完整：采用临时文件 + 原子替换，并在加载失败时捕获异常回退 DB。
