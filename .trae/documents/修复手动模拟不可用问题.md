## 现状与根因（已定位）
- 手动模式会禁用 Start/Stop，引导不清晰，用户容易误以为“不能运行”。
- 入队时不校验选择项，可能把 user/reader/resource 以 null 形式入队，执行阶段全部被跳过且无提示。
- 队列行解析依赖固定位置分词（parts[1..3]），脚本导入或空格变化会导致解析错位并静默 return。
- 手动执行不会记录 submitted 指标，界面长期显示 submitted=0，进一步造成“没生效”的错觉。
- 手动模式缺少显式刷新入口，用户/读卡器/资源下拉容易过期。

## 目标
- 手动模拟可用、可理解：能稳定入队、稳定执行、失败有提示、执行后统计与列表能反映变化。

## 修改方案
### 1) 手动模式交互优化（SimulationWorkbenchPanel）
- 在手动模式界面增加“刷新数据”按钮，直接调用 refreshData()。
- 手动模式切换时（switchMode）主动触发一次 refreshData()/refreshEventCombos，避免第一次进入下拉为空。
- 在手动模式显著提示“执行入口=执行队列”，避免只看到 Start/Stop 禁用。

### 2) 入队逻辑改为“按动作校验必填项”（SimulationWorkbenchPanel.queueEvent）
- 根据动作决定必需字段：
  - Swipe/UpdateBadge：必须有 user + reader
  - SubmitRequest：必须有 user + reader + resource
  - SetResource(…)：必须有 resource
  - StepTime：不需要 user/reader/resource
- 若缺少必需字段：弹窗或 feed 明确提示原因，并禁止入队。
- 生成队列行时只写入需要的 key=value（避免把 null 写进队列）。

### 3) 队列解析与执行“可容错、可反馈”（SimulationWorkbenchPanel.executeQueuedLine）
- 用“按 token 解析”的方式替代固定位置 split：从整行提取 action / user= / reader= / resource= / xN（允许字段缺失）。
- 对解析失败、缺字段、找不到 badge/reader/resource 的情况：在 feed 输出可读错误信息并跳过该行（不再静默失败）。
- 对会产生访问请求的动作补齐 submitted 统计：
  - Swipe（reader != null && badge != null 时）在调用 swipe 前 metrics.recordSubmitted()
  - SubmitRequest（badge != null 时）在 submit 前 metrics.recordSubmitted()
  - granted/denied 仍由现有 router accessListener 记录。
- SetResource(…) 成功后调用 refreshData()，保证下拉与列表同步。

### 4) 下拉数据来源修正（SimulationWorkbenchPanel.refreshEventCombos）
- user 下拉保持使用 badgeCode（仅加入非空），但当为空时给出“请先为用户创建徽章/生成演示数据”的提示。
- resource 下拉改为从数据库 loadAllResources() 填充（不再仅依赖 readerTable 的 resource_id），避免资源列表不全。
- reader 下拉继续从 router.getBadgeReaders() 填充。

## 验证方式
- 单元测试：为新的“队列行解析”提取一个可测试的方法，覆盖：
  - 缺字段、乱序 token、额外空格、无 xN 时默认 1
  - action 中文/英文的 normalize 兼容
- 运行 mvn test 确保回归为 0。
- 手工冒烟：生成演示数据 → 切手动模式 → 入队 Swipe/SubmitRequest/StepTime/SetResource → 执行队列，确认：
  - feed 有明确成功/失败信息
  - stats 的 submitted/granted/denied 正常变化
  - 资源受控状态变更后列表/下拉可刷新。

## 影响范围
- 仅修改 SimulationWorkbenchPanel（必要时增加少量 i18n key）；不改动核心路由/权限引擎逻辑。
